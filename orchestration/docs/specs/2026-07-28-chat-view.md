# chat-view — design (in planning)

> **Planning status.** Do not build yet. This is the arc's **4th** member, created when the arc's
> cross-cutting north-star question resolved into a concrete feature (Lior, 2026-07-28). It is built
> **last** by his sequencing.

## Origin

The continuation spec carried one open question: *must a place exist to see what you discussed, and in
what shape?* Lior's verbatim motivation: **"щоб побачити що ми писали до нього, не заходячи в меморі і
не копирсатись по тредам"** — i.e. the Memory window technically already shows thread contents, but
going there is the wrong frame and the wrong cost for "what did we just talk about."

Resolved during the voice brainstorm (same session): the answer is **not** a new surface and **not** a
chat app — it is an **expanded state of the answer widget**.

## Decided (firm)

### C1 — What it is

A third state of the answer widget: **the conversation as a feed, with the reply input at the bottom.**
Widget states are **"three+"** (extensible — Lior: later there will be other widget kinds, and widgets
shown inside widgets; three only because today we render text):

1. `minimized` — the persistent handle,
2. `expanded` — the answer + inline reply input,
3. `chat-view` — the feed + the same reply input.

`chat-view` is deliberately **not** the default expanded state: an answer that opens as a chat window
every time is exactly the "ChatGPT in the corner" feeling the product is built against, and it costs
vertical space on the hot path.

### C2 — Entry points

- **Primary: a button on the widget** (Lior: "там є кнопочка у віджетті, ти на неї натискаєш").
- **Tray item "Історія…"** — the no-live-widget path. Without it the feature has a hole: with nothing
  asked, reading yesterday's conversation would mean opening Memory, which is what the feature exists
  to avoid.
- **Optional hotkey**, `chatView.hotkey`, **unbound by default** (Lior).

**Rejected:** reusing the main (text) hotkey to open chat-view when idle. It would replace an empty
input with a wall of history on every invocation — the most expensive property of the product
(launcher feel) traded for a rare need.

### C3 — Geometry (Lior, verbatim)

Opens as a **right-half-of-screen panel, 70% of screen height, vertically centred on the right side.**

*Zone note:* this is larger than ADR-0006's top-right widget zone. Accepted because chat-view is an
**explicit reading mode**, not the hot path — the two-zone invariant (centre = input, right = results)
still holds for the daily cycle. Geometry is config-driven (`chatView.widthPct` / `heightPct`).

### C4 — The load-bearing invariant: read-continuous / write-tail-only

- **Write reaches only the live tail.** A turn is only ever added to the current conversation. No
  replying into a past conversation, no branching, no cross-thread roaming.
- **Read is continuous across past conversations** — but see C5: never automatically.

This is the line that keeps a history feed from being the rejected "chat app in a small window."
Lior's own framing of the difference: what he rejected at project start was *"сайдбар і там чати чати
чати"* — a thread-management app. One ordered feed read as history is a different thing.

### C5 — Scrollback: on by default, but the past never appears by itself

- `chatView.scrollbackEnabled`, **default `true`** (a feature whose point is seeing the past should not
  ship muted).
- **The past is never revealed by scrolling.** At the top of the feed sits an explicit button —
  **"завантажити що було раніше"** (Lior). Nothing older loads until it is pressed.
- **One click = one previous conversation** (not "50 more messages" — a message-count page would cut a
  conversation in half, and dividers are per-conversation anyway).
- The **same** button covers a very long current conversation: the initial load is capped
  (`chatView.initialTurns`), and the button first fills in earlier turns of the current thread, then
  moves on to previous conversations.

**Why this is better than lazy-load-on-scroll (and it was Lior's addition):** it makes the privacy
posture stronger than any toggle — even with scrollback enabled, a passer-by scrolling the panel sees
nothing older unless *you* ask for it. And it makes pagination **semantic** instead of mechanical.

### C6 — Dividers

Between conversations: relative/absolute date + the thread `title` when present (`threads.title` is
nullable — `packages/daemon/src/memory/schema.ts:44`).

### C7 — Erased conversations render as tombstones, never as gaps

2e `forgetThread` leaves husks (`threads.status = 'forgotten'`, content `[forgotten]`, title NULL). The
feed must show an explicit "this conversation was erased" row. A silent gap would make history lie.

**Do not "fix" the adjacent asymmetry:** a tombstoned conversation whose derived **facts still exist**
is *correct* — ADR-0012 Ruling 2 (fact source-independence) is structural.

### C8 — Closing

The same button, or `Esc`, **collapses back to `expanded`**. It does **not** dismiss the thread —
dismissing a conversation stays a separate, explicit action (ADR-0006 rule-of-three).

### C9 — Auto-minimize is suspended while chat-view is open

The continuation spec's ~5 s auto-minimize does not run in chat-view. You are in a reading mode; a
timer that shrinks what you are reading is precisely the Siri behavior the continuation design exists
to avoid. (Rule, not a config key — a setting here would be pointless.)

### C10 — Voice inside chat-view

Per voice-spec **D4**, the listening indicator is born **in the reply-input slot** — in chat-view that
is the bottom input. No new rule; the same slot.

### C11 — No search in v1

Deliberate. Search already exists in two places (the Memory window; `memory_search` for the agent).
Adding it here is a second feature, not a detail of this one.

### C12 — Content limit: the feed can only show what the archive stored, and the archive is text

`messages` is `role` (`user`|`assistant`) + `content TEXT`
(`packages/daemon/src/memory/schema.ts:47`). Therefore:

- chat-view is a **text transcript**;
- **past widgets cannot be re-rendered** — their structure was never persisted. Today the difference is
  nil (only the `text` primitive ships, per ADR-0009), but once route 4 lands, history will show a text
  trace of a widget-rich past. Making past widgets live would require a **new persistence surface**
  (tool-call payloads) which automatically creates a **new erase surface** for 2e forget → out of scope,
  recorded as O3;
- **widget interactions are invisible** (a `tool_result` is not a message and is stored nowhere). See
  [[widget-lifecycle-model]] §5. **Lean:** synthesize a compact, explicitly-marked user message
  (`[selected: blue]`) so the transcript reads coherently, with the marker letting the distiller ignore
  it — this is a memory write and would otherwise flow into fact derivation. **Decision deferred** to
  whichever of chat-view / route 4 builds first.

### C13 — `/history.html` is a vestige, and chat-view is the moment to retire it

`GET /history.html` exists (`packages/daemon/src/memory/history-page.ts`, routed at
`packages/daemon/src/index.ts:149`) — a loopback **web** page from Theme A. **Lior, 2026-07-28: "це
рудимент… можливо є сенс повністю його видалити, але воно не просить їсти, тому я залишив."**

So it is **not** a design partner for chat-view and must not be preserved-by-default. Recorded
recommendation: **delete it in the chat-view build** — once chat-view exists it has no remaining
purpose, the generic memory line already stopped pointing at its port URL
(`packages/daemon/src/memory/provenance-stamp.ts:7`), and removing it also removes an HTTP route with
its own token/Host-guard surface. Not a task for voice or settings; a cheap subtraction at the right
moment.

The **Memory window** stays authoritative for per-thread **operations** (forget-thread, fact
edit/forget, provenance). chat-view only reads.

### C14 — Config keys chat-view contributes to settings

| Key | Default |
|---|---|
| `chatView.hotkey` | unbound |
| `chatView.scrollbackEnabled` | `true` |
| `chatView.initialTurns` | initial turn cap of the current conversation |
| `chatView.widthPct` | `50` |
| `chatView.heightPct` | `70` |

## ADR-0012 rider — ACCEPTED (Lior, 2026-07-28)

> A **thread-scoped-writable, explicitly-loaded history view** is allowed as an expanded state of the
> answer widget (`chat-view`): a right-half panel (70% height) opened by a control on the widget,
> showing the conversation with a reply input at the bottom.
>
> - **Write reaches only the live tail.** A turn can only be added to the current conversation.
>   Replying into a past conversation, or branching, is not possible.
> - **Read is continuous, but never automatic.** The view opens on the current conversation; earlier
>   conversations are appended **only by an explicit "load earlier" action**, separated by dividers.
> - **No thread management.** No sidebar, no thread list, no picker, no cross-thread navigation. The
>   Memory window remains authoritative for operations on threads (forget, facts, provenance).
> - **The widget stays ephemeral.** chat-view is a *state* of a dismissible widget, not a persistent
>   surface; closing it returns to `expanded`.
>
> This **bends** decision 3 (output is ephemeral widgets, not a persistent scrolling chat log) and
> decision 4 (the user interacts with threads, not one infinite feed) **without discarding** either:
> the unit remains an ephemeral widget, interaction remains single-thread, and only **reading** becomes
> continuous — on demand.

**Status of this rider:** accepted by Lior in the 2026-07-28 brainstorm (§5.2 tier — it moves an
accepted ADR's decisions). It is owed to `adr/0012-conversation-and-memory-model.md` as a dated
in-file section, following that file's existing convention (Amendment 2026-06-13, Rider 2026-07-10).
**The doc-landing of the rider is a task; the decision itself is already made.**

## Open — carried

- **O1 — pagination read API.** Today's memory HTTP surface is per-thread (`GET /memory/threads` +
  thread detail). "Load earlier" needs **chronological cross-thread pagination**, plus an index: only
  `(thread_id, turn_index)` exists (`schema.ts:56`), there is no global time index.
- **O2 — rendering the `[selected: …]` synthesis** (C12) — decide with route 4.
- **O3 — persisting widget structure** so past widgets could re-render. Explicitly out; would add an
  erase surface for 2e.
- **O4 — very long feeds:** virtualization / trimming. `/history.html` already carries a token-trim
  precedent worth reusing rather than reinventing.
- **O5 — "hide history for a demo"** — a transient tray toggle distinct from
  `chatView.scrollbackEnabled`. Cheap, not designed.

## Not deciding here

Search (C11) · widget-lifecycle model (its own notes doc; route 4/5) · concurrent threads (route 5) ·
the settings surface itself (next arc member) · anything about voice beyond reusing D4.

## Behavioral DoD sketch (for the eventual build)

A live demo must show: a button on the widget opens the right-half panel; the current conversation reads
top-to-bottom with the reply input at the bottom; **scrolling up reveals nothing** until "завантажити
що було раніше" is pressed; one press loads exactly one previous conversation with a divider carrying
its date/title; an erased conversation shows a tombstone row (and a fact derived from it still exists in
the Memory window — correct, not a bug); a reply typed in chat-view lands on the **current** thread and
the feed snaps to the tail; a voice turn shows its indicator in the **bottom input slot**; `Esc`
collapses to `expanded` **without** dismissing the thread; the auto-minimize timer does **not** fire
while chat-view is open; and `chatView.scrollbackEnabled=false` hides the load-earlier button entirely.
