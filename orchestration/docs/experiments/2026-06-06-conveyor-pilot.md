## Що саме змінюється

- **Топологія Z (federated):** кілька окремих top-level чатів, не один cockpit зі субагентами.
  Кожен воркер-чат — самостійна сесія (може мати власних субагентів; обмеження «глибина 1» зникає).
- **Hub-and-spoke, асиметрія:** слухає шину/чергу **тільки Jimmy** (довгоживучий). Воркери —
  **fire-and-complete**: запущені багатим брифом, женуть чанк агентно до кінця/гейта, постять
  результат, завершують хід і вмираються (`tmux kill-session`). Воркери ніколи не «підписані».
- **Білінг:** усе — **інтерактивні** `claude`-сесії (без `-p`) → **підписка**. Метрований
  Agent-SDK-пул (з 2026-06-15) НЕ зачіпається, бо гачок — саме прапор `-p`/SDK, а не fan-out.
  (Див. reference-пам'ять про білінговий кордон; tmux-detach-білінг — у чек-листі нижче.)
- **Гейти:** воркер постить `BLOCKED` + вмирає → Jimmy ескалює Lior → Lior вирішує →
  Jimmy піднімає **свіжий continuation-воркер** зі стану на диску (рестарт > воскресіння).
- **Драбина запуску:** crawl (авто-бриф + self-serve доки) → walk (PR auto-review) → run (шина).
  **Пілот стартує на crawl.** Шину будуємо лише якщо залишковий копі-пейст це виправдає.

## Рішення на 2026-06-13 (або після мерджу MF-04+MF-05)

- **ТРИМАТИ + лізти драбиною** (додати walk/run) — якщо: **0 bad-main** AND Lior-дотики
  суттєво < baseline AND якість не впала.
- **ДОКРУТИТИ (лишитись на conveyor)** — якщо toil впав, але релеї/надійність ще погані →
  будуємо шину АБО лагодимо брифи.
- **ВІДКОТИТИ на half-manual** — якщо: будь-який bad-main safety-провал, OR toil не впав,
  OR якість регресувала, OR conveyor з'їдає більше часу, ніж економить.

## Пілотні знахідки (crawl rung) — MF-04 + MF-05-T1

> **Провенанса:** перший кондуктор помер на 529 (2026-06-06) до того, як записав знахідки
> на диск — канонічний список жив лише в його контексті. Нижче — **реконструкція** з
> relaunch-брифу, ledger і git (нумерація #3/#5 заякорена брифом). Урок «стан живе на
> диску» — сам Finding #1; ця секція і є його виконанням.

1. **Стан кондуктора живе на ДИСКУ, не в контексті чату.** 529 вбив кондуктора посеред
   шефердингу MF-05; втратилась лише in-context бухгалтерія (TodoWrite-таски) — **нуль
   втраченої роботи**, бо git/ledger/чанк-файли тримали все. Правило: кожна
   ескалація/рішення → у ledger одразу, не «потім». (Це підтверджує дизайн-тезу §11.1
   «disk canonical, chat disposable» — relaunch з диска спрацював на практиці.)
2. **Спи, поки воркер будує.** Кондуктор, що «когітує» паралельно з воркером, палить
   спільний subscription-cap і провокує 529-і. Прокидайся на ledger-подію / довгий
   heartbeat. І **не воюй з 529**: довгий back-off; якщо тримається — пауза + сигнал Lior,
   не молотити ретраями.
3. **Один воркер на спільне робоче дерево** (немає git-worktree-ізоляції на crawl).
   Верифікація/мердж — тільки на ЧИСТОМУ checkout/worktree, ніколи на дереві воркера.
   Кандидат на walk-rung: worktree-ізоляція воркерів.
4. **Анти-self-split.** MF-05-воркер сам розрізав чанк на T1/T2 на архітектурному гейті
   (ADR-0013). Lior благословив *цей* розріз як принциповий — але правило надалі:
   воркер постить `BLOCKED: re-decompose` (+ пропонований розріз як флаг), не
   self-tranche. Розмір чанка — авторитет decompose-шару (та сама §7.2-асиметрія
   контексту). → внесено в engine-orchestrator skill (Authority).
5. **Жоден `status: proposed` ADR не їде feature-PR'ом у main.** ADR-acceptance —
   §5.2-гейт Lior; мердж із proposed-ADR у диффі або «заморожує» неухвалене рішення,
   або лишає сироту в доках. → доданий у пре-мердж чек-лист Джиммі (перевірено на
   PR #28: ADR-0013 acceptance дочекались ДО мерджу T1 ✓).
   *Follow-up (reviewer-флаг, 2026-06-10):* зараз це правило кодифіковане лише в
   engine-orchestrator skill + тут — на pilot-review 2026-06-13 вирішити, чи внести його
   в сам PIPELINE §5.2 precondition-set (щоб skill не був єдиним джерелом
   merge-blocking правила; PIPELINE-правка = Lior-рівень, не Джиммі).

6. **Спільне дерево — це і дерево Lior'а.** Кондукторський коміт упав на локальний main, бо
   Lior перемкнув гілку робочого дерева між кроками кондуктора (паралельна людська робота —
   PR #31). Виправлено cherry-pick'ом без пушу main. Правило: `git branch --show-current`
   перед КОЖНИМ комітом у спільному дереві; ніколи не припускати, що дерево там, де ти його лишив.
7. **claude-CLI process-title = номер версії** (напр. `2.1.170`), не `claude` — детектор
   живості воркер-пейна має інвертувати логіку («вийшов» = пейн повернувся до шела/dead),
   а не whitelist'ити імена процесів (перший монітор дав false-positive WORKER-EXITED).
8. **Воркер самосертифікував свій мердж** (CM-01, PR #33): реконсильований skill каже
   «auto-merge on all-green» (§5.1), але crawl-щабель кладе мердж на кондуктора ПІСЛЯ
   незалежної переверифікації (§11.4) — skill цього шару не кодує. Обійшлося (пост-фактум
   перевірка зелена), операційно залатано conductor-override'ом у брифах (DONE-ready-to-merge).
   ⚠️ Тензія §5.1↔§11.4 (хто виконує мердж на crawl) — Lior вирішує на pilot-review разом із
   колізією «Finding #5 vs async-ADR-acceptance» (ADR-0014 поїхав на main як proposed за
   ruling'ом, закодованим декомпозером у чанку; обидві політики зараз співіснують).

### Що далі (climb-as-harden)

1. **walk-щабель — CI** (tests + `lint:strict` + typecheck у GitHub Actions) + branch protection +
   auto-revert на червоний main. Це замінює ручну re-verify кондуктора автоматичним нетом і
   **знімає єдину крихкість crawl**. Найвищий пріоритет харденінгу.
2. **Re-confirm білінгового кордону ≥2026-06-15** ([[reference_claude_code_automation_billing]]).
3. **worktree-ізоляція воркерів** (Finding #3 candidate) — лише якщо паралельні воркери стануть потрібні.
4. **Шина (run) — ПАРКА.** Будувати лише якщо залишковий agent↔agent-транспорт це виправдає; релеї=0
   зараз не виправдовують. Un-defer concurrent-session моделі + ADR — на той момент.
